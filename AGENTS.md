# AGENTS.md

Instructions for AI coding agents working on **Suomi Sniper** (Vite + Three.js,
vanilla JavaScript, no framework).

Read `README.md` first for what the game is and how to run it, and
`HANDOVER.md` for the current state — what is known-good and what has not been
verified. This file is about *how* to work on it.

## Commands

```sh
npm install
npm run dev       # dev server with hot reload
npm run build     # static output to dist/
npm run preview   # serve the build
```

No test runner and no linter are configured. Adding one is welcome, but say so
rather than assuming it exists.

## Architecture

Five layers. Code goes in the one it's named for, and dependencies only point
one way.

| Path | Holds |
| --- | --- |
| `src/data/` | Static content — the map definitions. |
| `src/scene/` | Anything that creates 3D objects. Geometry, materials, enemy figures, the first-person weapon. |
| `src/game/` | Rules and state — exposure, health, scoring, audio. Must not create meshes. |
| `src/services/` | start.ng integration. |
| `src/ui/` | DOM and styling. Must not touch Three.js. |

`main.js` is the only file that knows about all of them. `scene/` must not import
from `game/`, `ui/` or `services/`; `game/` may import `scene/` (it drives enemy
figures) but not `ui/`.

## Conventions

**Procedural assets only.** No `.png`, `.glb`, `.mp3` or `.fbx` in `src/`. Every
texture is drawn on a `<canvas>`, every sound is an oscillator or filtered
noise. The exceptions are `public/cover.png` (generated by `tools/cover.html`)
and the Google Fonts link in `index.html` — both deliberate.

**Comment the why.** The existing comments explain decisions that would
otherwise look arbitrary: why the sights are DOM, why the launch solve includes
the curve, why line of sight checks a tree list, why exposure decays differently
per weather. A comment restating the next line is noise.

**Units are metres**, and the pitch is oriented so the player sits at positive z
looking toward negative z. `LINE_Z` is 0. Don't introduce a second scale or a
second orientation.

**Interface is DOM, not 3D.** Text and controls live in `src/ui/` and
`src/styles.css`. Don't add text geometry or sprites. The one deliberate exception
is the weapon view model in `scene/weapon.js`, which is geometry in a scene of its
own — see the note on the render pass below.

**The canvas and the scope are the game.** Two things to re-check after any
change:

- The canvas must exactly fill the viewport at every window shape. `main.js` calls
  `renderer.setSize(w, h, false)` on purpose: the `false` stops Three writing
  inline pixel dimensions onto the canvas, where they beat the stylesheet and
  paint the game into one corner of the screen. Do not drop it, and do not
  replace the `ResizeObserver` with a bare `window.resize` listener.
- The scope window is `--scope-d` across (76 vmin by default) with an opaque
  surround. Check the hairlines stay centred and the window stays inside the
  viewport at 1280×800, 700×900 and 390×780.
- The centre dot must show in **every** view, including first person at the hip.
  The rifle view model sits low and right of frame and does not lie on the aim
  line, so without the dot a hip shot is fired with no reference at all — which
  reads to a player as "the gun doesn't shoot". The dot is hidden under the
  scope, which draws its own centre.

**One hit radius.** `HIT_RADIUS` in `game/round.js` decides both what a shot
connects with and whether the target bracket turns orange, and `probe()` returns
a `lethal` flag derived from it. Never let the UI decide "on target" from a
different number than the one the shot uses, or the reticle starts lying.

**The weapon is a second render pass.** `scene/weapon.js` is drawn after the world
with the depth buffer cleared, using its own fixed-FOV camera. That is what stops
the rifle clipping into trees and stops its own parts drawing through each
other. Keep it out of the world scene, and keep its camera FOV fixed — the scope
zoom must not magnify the stock.

## Boundaries

- **Never commit binary assets** without asking first. See above.
- **Never hardcode a URL that should be relative.** `base: './'` exists so the
  build works from a subdirectory; absolute asset paths break start.ng.
- **Don't raise the pixel ratio** above 2 or the shadow map above 2048. Both are
  tuned for mid-range phones.
- **Don't add a framework.** The UI is a few hundred lines of DOM.
- **Don't put a password field anywhere.** start.ng handles sign-in and its
  publisher rejects games that ask for one.
- **Keep the game playable with no start.ng connection.** The connect page is
  silent outside `*.start.ng`, and the game must still run.

## Tone and subject

The winter setting is atmosphere, not a reconstruction. The owner has asked for
modern optics, so the historical no-scope constraint no longer applies — do not
reintroduce it as a rule. Still: no gore, no glorification, no real-world
political content, and the enemies stay generic infantry. If a change would make
it a "shoot the foreigners" game rather than a stealth game, it's the wrong
change.

## Verifying a change

There's no automated check, so verify by hand and say what you actually did:

1. `npm run build` must complete without errors.
2. `npm run dev`, then play a full round on each of the four maps.
3. Confirm the core tension still works: fire twice in quick succession and you
   should be found; stay still and the exposure meter should come back down.
4. Resize the window, including a narrow one: the canvas must fill it rather than
   sit in a corner. Raise the scope and confirm the glass is centred, the wheel
   switches ×4/×8, and the bracket still finds a man.

State plainly what you could not test. "The build passes and I played a round on
Kollaa" is useful. "It works" is not.
